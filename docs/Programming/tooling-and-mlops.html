Tooling & MLOps

A backtest you can't reproduce isn't a result — it's an anecdote. The gap between a notebook that "worked once" and infrastructure a desk can trust is engineering discipline: versioning your code, pinning your environment, tracking every experiment, and shipping models as services. This page is that toolchain.

1. Version control with Git & GitHub​

Git records the full history of your code, so you can reproduce any past state, experiment safely on branches without breaking main, and collaborate. GitHub hosts it and adds pull requests, issues, and CI/CD. The everyday loop:

git clone <repo-url>          # grab the project
git checkout -b new-signal    # branch off to experiment safely
# ...edit code...
git add .                     # stage changes
git commit -m "add momentum signal"   # snapshot with a message
git push origin new-signal    # publish the branch; open a Pull Request to merge

A .gitignore keeps junk (data dumps, .env secrets, __pycache__) out of the repo. Why a quant cares: your reported Sharpe is only credible if you can point to the exact commit that produced it. Version control is what turns "I got 1.8 once" into "here is the reproducible pipeline." (This very site deploys on every git push — code is the source of truth.)

2. Reproducible environments with Docker​

The oldest bug in software is "but it works on my machine." Docker kills it by packaging your code plus its entire environment — OS libraries, Python version, dependencies — into a portable image. Run that image anywhere and you get an identical container.

# Dockerfile — a reproducible research/serving environment
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "backtest.py"]
docker build -t my-strategy .     # build the image
docker run my-strategy            # run it — same result on any machine

For multi-service stacks (a model API + a database + a dashboard), docker-compose wires them together in one file. Why a quant cares: the container your research ran in is the container production runs in — no more "the model behaves differently live" surprises from a mismatched library version.

3. MLOps — from notebook to production​

MLOps is DevOps for machine learning: the practices and tools that get a model from your laptop into a reliable, monitored, reproducible pipeline. Three pillars:

Experiment tracking — MLflow​

When you're trying 50 model variants, memory and a spreadsheet won't cut it. MLflow logs the parameters, metrics, and model artifact of every run, so you can compare them and reproduce the winner exactly.

mlflow ui        # launches a dashboard of every logged run, ranked by metric

Each run records what settings produced what score, with the trained model attached — the antidote to "which config gave me that 0.62 accuracy again?" (Dagshub is a hosted platform that bundles MLflow tracking and DVC storage together — think GitHub, but for ML experiments and datasets.)

Data & model versioning — DVC​

Git is built for code, not multi-gigabyte datasets. DVC (Data Version Control) is "Git for data": it versions large datasets and model files, storing them in cloud/remote storage while tracking lightweight pointers in Git.

dvc add data/prices.parquet     # start versioning a big dataset
git add data/prices.parquet.dvc # commit the small pointer, not the file
dvc push                        # send the actual data to remote storage

Why a quant cares double: a result must tie to an exact data snapshot. If your dataset silently changes (a vendor restates history), your "reproducible" backtest quietly becomes irreproducible — and restated data is a classic source of look-ahead bias. DVC pins the data to the result.

Model serving — BentoML​

A trained model sitting in a .pkl file does nothing. BentoML (and similar tools) package it into a production API — a service that takes features over HTTP and returns predictions — with the environment baked in for consistent deployment.

bentoml serve service:latest      # your model is now a live prediction API

And then: monitoring​

Deployment isn't the end. Markets drift, data pipelines break, and a model that was sharp last quarter can rot. Production MLOps monitors inputs and predictions for drift and triggers retraining — closing the loop back to the ML lifecycle.

The toolchain at a glance​

ToolJobQuant payoff
Git / GitHubVersion codeReproducible research; safe experiments; a commit per result
DockerVersion the environmentResearch == production; no dependency surprises
MLflowTrack experimentsCompare runs, reproduce the winner, no lost configs
DVCVersion data & modelsTie every result to an exact data snapshot
BentoMLServe modelsTurn a signal into a live API

None of this makes a strategy profitable — but all of it is what makes a strategy trustworthy and shippable, which is exactly the difference between a student notebook and desk-grade work.
